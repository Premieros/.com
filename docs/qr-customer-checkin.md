# Customer phone entry and active-order recovery

The customer enters a phone number, adds a name only for a new branch-local profile, then chooses delivery or a table. A new customer is never asked for a recovery PIN. The first successfully submitted request returns a two-digit code once; the client displays it prominently and retains it on that device for the visit. A lost response or forgotten code can be recovered by an authorized employee issuing a new code.

An already trusted device resumes its own active visit directly. A new device with an active phone must provide the two-digit code. Three failed attempts lock recovery until authorized staff issue a new code. Recovery transfers the device capability and request/call hashes atomically, invalidating the former device. The PIN is salted and hashed; neither private profiles nor visits have API table grants. These profiles do not adopt CRM credit accounts by unverified phone number.

Dine-in captures a compact JPEG through the camera, then asks the customer to select the number shown. The private photo is available only to branch staff. The first acceptance requires a staff photo confirmation. Staff can assign another available table initially; further changes use the existing POS table-transfer workflow. A camera photo can be replayed and is not proof of physical presence. Staff verification and closing the visit are the operational boundary. Closing/cancelling/deleting the bill invalidates the visit; staff can also end access independently when a guest leaves. Visits additionally expire after 24 hours. Delivery remains available remotely and uses the canonical service-order RPCs and current product prices.

Apply `20261114093244_customer_checkin_qr_table_ordering.sql` only after review and passing checks. It defaults `checkin_enabled` to false, preserving existing public RPC behavior during deployment. Deploy the client before enabling phone entry in each branch's customer-order settings. Enabling entry gates legacy submission/menu/tracking RPCs; old browser tabs must reload. Already accepted financial orders are not rewritten or assigned to an unverified phone. Do not infer ownership of a legacy order from its table, ID, or a newly supplied phone.

Private cores remain owner-only; invoker RPC wrappers grant only their intended guest/staff operations. Staff approval uses existing role/branch/operator permissions, authoritative pricing and QR revisions. A POS workspace with unsaved changes cannot accept an addition to its current table or delivery bill. Unrelated requests can be accepted without leaving the workspace.

Verification includes PGlite security/lifecycle tests, component tests of new entry and recovery, camera cleanup, photo confirmation and delivery workspace protection, plus concurrent PostgreSQL retries and PIN locks in CI. All financial tests use disposable databases. Avoid creating or accepting test invoices on production.

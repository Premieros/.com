## 1. تعريف المنتج ومبدأ التطوير

- المنتج: Premier OS — نقاط بيع، تشغيل مطاعم، ومخزون/مشتريات/تصنيع وتكاليف ومحاسبة وتقارير وصلاحيات متعددة المؤسسات والفروع والمخازن.
- اللغة العربية أساسية مع دعم واجهة ثنائية اللغة. واجهة Windows يفترض أن تطابق واجهة الويب، لا تصبح تطبيقًا منفصلًا بمنطق محاسبي مختلف.
- استراتيجية التطوير التي اختارها المستخدم: تصحيح العلاقات والمصدر القانوني للبيانات أولًا (الفروع والمخازن والمخزون والمبيعات والمشتريات وBOM والتكلفة والمحاسبة)، ثم الميزات المتقدمة، ثم وكلاء AI بعد استقرار الأذونات والمحاسبة والتدقيق.
- تجنّب إعادة كتابة النظام كاملًا أو بناء قاعدة مالية متوازية غير متوافقة؛ راجع docs/architecture/PREMIER_ARCHITECTURE_V2_BLUEPRINT.md.
- معيار المنتج: **Simple inside, complete outside, correct data first**.

## 5. المتطلب المعتمد: Premier Local Network + الهاتف + المطبخ

**قرار المستخدم، 2026-11-08:** كل فرع يستخدم حاسوب Windows رئيسيًا وخادم محليًا؛ هواتف الويتر وشاشات المطبخ والكاشير على نفس Wi-Fi/LAN تستخدم Premier **دون إنترنت خارجي**، والتغييرات تنتقل لحظيًا. عند عودة الإنترنت يزامن الفرع مع Supabase. يجب أن تصل الشاشات الجديدة ضمن تحديث Windows الموثوق؛ لا تحديث JavaScript عن بعد بلا تدقيق.

### نموذج الاستخدام المعتمد
1. يعمل Windows كخادم فرع واحد، وقاعدة بيانات عمليات الفرع على الخادم، لا على كل هاتف منفردًا.
2. هاتف الويتر يفتح عنوان HTTPS محليًا (اسم نطاق محلي يعتمد على DNS وشهادة موثوقة، أو IP/اسم فعلي داخل شبكة الفرع بعد الإعداد) ويُصادق المستخدم ويرتبط بجهاز مصرح به.
3. ينشئ الويتر طلبًا بمعرّف فريد وجدول وحالة مُحكمة؛ يُحفظ على خادم الفرع بعملية ذرية.
4. تُرسل تذكرة الحدث إلى KDS بالفرع ومركز التحضير الصحيح عبر WebSocket أو SSE محلي مع استرداد أحداث بعد الانقطاع؛ الطاهي يُحدث الحالة «جديد -> تحضير -> جاهز -> قُدّم» وفق الدور.
5. يُخبر السيرفر كل هواتف الفرع بالمستجدات؛ لا ينبغي أن تستجيب شاشة مطبخ لفرع أو محطة غير مصرح بها.
6. الكاشير يفتح الفاتورة ويُحاسب وفق العقد المحلي القانوني؛ لا يُعلن دفع «مُرحّل للسحابة» حتى تأكيده.
7. عند عودة الإنترنت: يصادق الخادم ويزامن outbox بمفاتيح فريدة وACK، ثم يحل تعارضات المخزون/الحسابات أمام المشغّل، ولا يعيد الطباعة تلقائيًا.
8. توقف جهاز Windows/الراوتر يوقف مشاركة LAN حتى إن كانت الأجهزة مشحونة؛ يلزم UPS وإشعار صحة وتخطيط الاسترداد.

### بوابات قبول LAN الملزمة
- لا يُقدَّم رابط LAN خارجي فعلي قبل TLS موثوق وشهادة نافذة وإقران أجهزة وصلاحيات قابلة للإلغاء.
- دون WAN: فتح الهاتف/تسجيل الدخول المحلي المصرّح، إنشاء طلب، ظهور KDS، تغير حالات الطهي، حفظها وإعادة فتحها عند إعادة التشغيل.
- أجهزة متعددة في نفس الفرع: الطلب الواحد لا يتكرر؛ حجز ترقيم؛ optimistic concurrency؛ حالات تعارض واضحة؛ أذونات الويتر لا تسمح بالتعديل المالي للمحاسب/المدير.
- جهاز في فرع آخر أو جهاز غير مقترن لا يرى طلبات الفرع ولا يستطيع تحديث حالات المطبخ.
- اختبارات فقدان الطاقة، استئناف LAN/WAN، قاعدة محلية تالفة، انقطاع طباعة، 3+ أجهزة، وعمليات بيع متزامنة.
- يجب التمييز في واجهة الموظف بين «محلي محفوظ» و«تمت المزامنة مع السحابة».
- يراجع أولًا branch-hub الموجود؛ لا ننشئ Hub مكررًا بقاعدة ثانية أو ننقل المبيعات الحية تلقائيًا.

**حالة التنفيذ:** المتطلب معتمد، كود Branch Hub التأسيسي موجود. تشغيل هاتف الويتر + شاشة KDS مشتركة من LAN **لم يجتز بعد اختبارًا وظيفيًا** ولم يُدمج في Windows المثبت؛ لا تصفه بأنه جاهز.
